# 전표 이미지 처리: 동작·검증·성능

Green House에서 코어를 사용·수정할 때 필요한 기술 기준입니다. 기록일은 2026-10-16이며 아래 테스트·성능 수치는 기존 실행 결과입니다. 이번 문서 정리에서 새로 측정하지 않았습니다.

## 1. 처리 흐름

코어는 Java 21과 OpenCV 4.9.0-0으로 동작합니다. Spring·HTTP·DB에 의존하지 않으며 OCR이나 GPU를 사용하지 않습니다. 입력은 사진의 `byte[]`, 출력은 `ProcessingResult(report, images)`입니다. `images`는 파일명 → PNG 바이트의 Map이며 `report`는 Java record입니다. 디스크 저장은 호스트가 담당합니다.

| 단계 | 처리 | 결과·실패 시 동작 |
|---|---|---|
| 입력 정규화 | 이미지 디코딩, EXIF 방향 반영, 긴 변을 maxDimension 이하로 축소 | 작은 입력은 확대하지 않음. 빈 입력·20MiB 초과·디코딩 실패·60MP 초과 거부 |
| 방향 보정 | 표선 방향·상하 인쇄 밀도로 0/90/180/270도 추정 또는 수동 회전 | 수동 지정도 비스듬한 기울기 보정은 계속 수행 |
| 원근·기울기 보정 | 외곽 컨투어의 네 점 검출, 원근 변환 | 네 점이 없으면 표선으로 평면 변환 추정, 불확실하면 기울기 보정 후 사진 유지 |
| 표·격자 검출 | 적응형 이진화와 가로·세로 morphology opening, 선 투영으로 경계 추출 | 안정적인 표가 없으면 빈 행을 제거하지 않음 |
| 빈 행 판정 | 격자 제거 → 반복 인쇄 추정·제외 → 남은 연결 성분·잉크 비율 분석 | 상단 보호 행과 높이가 다른 제목/병합 행 보존, 표별로 빈 행을 잘라 이어 붙임 |
| 종이 분리 | Lab 색상·GrabCut·외부 컨투어로 배경 분리, 보이는 겹침 경계에서 분할 | 경계가 불확실하면 합친 영역 유지. 윤곽 밖을 투명 PNG로 출력 |

반복 인쇄는 유사 높이의 후보 행이 5개 이상일 때 행을 정규화하고, 70% 이상에서 반복되는 픽셀 주변을 고정 패턴으로 추정합니다. ‘특상·특·상·보’를 문자로 읽는 방식이 아니므로 같은 흑백 필기가 반복되면 오인할 수 있습니다. 파란 잉크는 별도 색상 마스크로 보존합니다.

종이 개수와 표 개수는 다릅니다. 한 전표에 두 표가 있어도 관측한 종이 경계가 없으면 두 장으로 나누지 않습니다. 전표 분리는 표별 빈 행 축약과 별도 처리이며, 가려진 내용을 복원하지 않습니다.

## 2. 결과와 조정 값

### 사용할 결과

| 결과 | 용도 |
|---|---|
| `01-corrected.png` | 회전·원근을 보정한 전체 사진. 빈 행은 잘라내지 않음 |
| `table-XX-compacted.png` | 검출된 표에서 빈 행을 실제 제거한 영상 |
| `paper-XX.png` | 전표별로 분리한 투명 배경 PNG. 빈 행은 잘라내지 않음 |
| `report` | 보정 방식, 회전, 표·행·종이 좌표, 제거 사유, 경고·검토 필요 여부 |

표·종이 PNG는 검출됐을 때만 존재합니다. `report.json`은 데모가 report를 직렬화한 파일이며, 코어가 JSON이나 파일을 직접 저장하지는 않습니다. 표·행·종이 좌표는 최종 보정 영상 기준이고 `documentCorners`만 EXIF 반영 후 원본 영상 좌표입니다. `reviewRequired`는 검토 필요 표시이며 신뢰도 점수나 정확도 확률이 아닙니다.

### 주요 옵션

| 옵션 | 기본값 | 사용할 때의 기준 |
|---|---:|---|
| maxDimension | 2200 | 800–3000. 낮추면 처리량·메모리를 줄일 수 있지만 작은 필기가 사라질 수 있음 |
| rotationDegrees | -1 | 자동. 오판하는 양식은 시계 방향 0/90/180/270도로 지정 |
| protectedTopRows | 2 | 각 표 상단 보존 행 수, 1–10 |
| ignoreRepeatedPrint | true | 반복 인쇄 제외. 동일 흑백 필기가 반복되는 양식은 false로 비교 |
| minimumInkRatio | 0.00035 | 빈 행 판정 잉크 비율, 0–0.1. 높이면 필기 있는 행을 삭제할 위험도 증가 |
| minimumComponentArea | 8 | 기준 크기의 작은 잡음 제거 면적, 2–1000 |
| outputMode | ALL | 운영 호출은 PRODUCTION을 명시. 검토할 때 REVIEW, 상세 진단은 ALL |

`PRODUCTION`은 전체 보정·검출된 표/종이 PNG와 report, `REVIEW`는 여기에 행 판정·종이 윤곽 표시, `ALL`은 선 표시와 수평·수직·종이 마스크까지 생성합니다. 선택하지 않은 진단 영상은 복제·그리기·PNG 인코딩부터 생략합니다. 모드 간 보고서·공통 PNG 동일성은 테스트합니다.

길이 임계값은 `s = min(원본 긴 변, maxDimension) / min(원본 긴 변, 2200)`에, 면적은 `s²`에 비례합니다. 색상·각도·잉크 비율은 유지하며 내부 최대 900px 종이 분석은 별도 좌표계 배율을 적용합니다. 비례 조정은 저해상도에서 같은 판정을 보장하지 않습니다. 최종 보정 캔버스는 회전·원근 변환 때문에 maxDimension보다 커질 수 있습니다.

## 3. 실행·메모리 계약

- `SlipProcessors.bounded(...)`로 생성한 인스턴스 하나를 Spring 싱글톤으로 공유합니다. `process()`도 같은 제한 실행기에 제출하고 기다리며, `processAsync()`는 Future를 반환합니다. 저수준 `new SlipProcessor()`는 제한을 우회합니다.
- 기본은 worker 2개·대기열 4개·OpenCV 내부 스레드 1개입니다. 한도는 실행기 인스턴스별이며, 포화되면 `ProcessingRejectedException`으로 즉시 거절합니다. OpenCV 스레드 설정은 JVM 전체에 적용됩니다.
- 비동기 loader는 worker 확보 후 파일을 읽으므로 대기열에 원본 바이트 전체를 보관하지 않을 수 있습니다. 호스트는 요청 종료 후 사라지는 업로드 임시 파일의 수명을 별도로 관리합니다.
- Mat·ROI·커널·컨투어·PNG 인코딩 버퍼의 픽셀 참조는 단계별 scope/finally에서 명시적으로 release합니다. 호출자는 Mat을 받지 않으며 반환된 PNG byte[]와 파일 저장 메모리를 관리합니다. Java Mat wrapper의 native header 삭제에는 finalization 동작도 남아 있습니다.
- 취소·interrupt는 실행 중 JNI 연산을 즉시 멈추지 않습니다. 실제 반환까지 worker를 점유합니다. 같은 worker의 loader/callback에서 같은 실행기로 동기 재진입하거나 close하지 않습니다.
- Bean 종료 시 close를 호출합니다. 종료 대기 한도 초과는 예외로 알리며 실행 중 native 작업이 남을 수 있습니다.

`-Xmx`는 native 메모리까지 제한하지 않습니다. 입력은 축소 전에 디코딩하므로 maxDimension만으로 원본 디코딩 메모리를 제한할 수 없습니다. worker/queue 제한도 호스트의 업로드 버퍼·완료 결과·ZIP·파일 저장 메모리를 제한하지 않습니다.

## 4. 검증한 범위

### 자동 테스트와 이식

검증 환경: Windows x64, Temurin Java 21.0.9, OpenPnP OpenCV 4.9.0-0. 코어/데모 Maven 빌드는 Maven 3.9.9·데모 Spring Boot 3.5.0을 사용했습니다.

| 검증 | 기존 결과 | 범위 |
|---|---|---|
| 코어 테스트 | 54개 통과 | 회전 17, 종이 분리 8, 처리 엔진 6, 해상도 10, 자원 수명 4, 제한 실행기 8, 공개 API 경계 1 |
| 데모 테스트 | 8개 통과 | HTTP·배치·Bean 종료. Green House에 복사하는 테스트에는 미포함 |
| Green House Gradle 코어 테스트 | 54개 통과 | 호스트 main `6c4232158939b4eabc8511889514bbcef63f76aa`, Java 21·Boot 4.1.0·Gradle 9.5.1 |
| Green House 패키징 | Boot JAR 생성 확인 | 코어·OpenCV JAR 포함. 로컬 Maven install 없이 project 의존성 사용 |
| Green House backend 전체 테스트 | 793개 중 792개 통과 | 기존 아키텍처 검사 1개가 Windows 경로 구분자 처리로 실패. 전체 통과로 간주하지 않음 |
| 이식 스크립트 | 설치·기존 모듈 거부 확인 | Git Bash에서 확인. 실제 Ubuntu 실행 검증은 별도 |

코어 테스트는 합성 영상과 실제 native 연산으로 잘못된 입력, 회전·원근·빈 행 판정, 겹침 분리, 해상도별 판정, Mat 해제, 모드 간 동일성, worker/queue·취소·종료·예외 복구를 검사합니다. 원본 사진 없이 실행할 수 있습니다. 실제 업로드·파일 저장·권한·Linux native 기동의 호스트 통합 검증은 아직 포함하지 않습니다.

### 실제 사진

기존 기본 2200px 실행은 JPEG 18장 모두 완료했고 종이 후보 PNG 31개, 표 영역 32개, 제거 행 61개를 생성했습니다. 자동 회전 13장·수동 지정 5장이므로 자동 정방향 판정 18/18 성공을 뜻하지 않습니다. 문서 네 모서리 확정은 0장, 표선 기반 원근 보정은 17장, 기울기 보정만 적용한 사진은 1장이었습니다. 종이 분리는 문서 네 모서리 검출과 별도로 동작합니다.

같은 원본 3장을 1100/2200/3000px로 처리했을 때 표·종이 개수는 유지됐지만 제거 행 수는 달랐습니다.

| 입력 파일 | 표 / 종이 | 1100px 제거 행 | 2200px 제거 행 | 3000px 제거 행 |
|---|---:|---:|---:|---:|
| 20260816_091446.jpg | 2 / 2 | 6 | 3 | 3 |
| 20260816_091908.jpg | 2 / 1 | 6 | 6 | 5 |
| 20260816_092640.jpg | 1 / 1 | 7 | 7 | 7 |

전체 사진의 행·윤곽 정답 라벨은 없습니다. 위 수치는 실행 결과이며 빈 행 판정 정확도·오삭제율·윤곽 IoU 측정값이 아닙니다. 사진과 출력 갤러리는 Git에 포함되지 않으므로 clone만으로 사진 실험을 재현할 수는 없습니다.

### 유지해야 할 한계

- 자동 상하 판정 오류가 실제로 있었습니다. `20260816_092020.jpg`는 AUTO가 180도로 오판해 최종 실행에서 0도로 지정했습니다.
- 반복된 흑백 기입을 고정 인쇄로 오인하거나 흐린 필기를 놓칠 수 있습니다. 중요한 전표는 REVIEW 결과와 원본을 비교합니다.
- 3장 겹침은 일반화 검증되지 않았습니다. 좌우 겹침을 세로 경계로 나누는 로직은 없으며, 교차·심한 구김·같은 색 배경도 취약합니다.
- 종이 윤곽은 근사입니다. 작은 배경·손가락이 포함될 수 있고, 겹친 여러 종이에 하나의 평면 원근 보정을 적용하는 것도 근사입니다.

## 5. 처리 시간·자원 실측

### 측정 조건

2026-10-16 Windows x64 / Java 21.0.9 / OpenCV 4.9.0-0에서 측정했습니다. 입력은 `20260816_091446.jpg`, 3000×4000 JPEG 약 3.03MiB, 자동 회전·maxDimension=2200·`-Xmx1200m`입니다. 단일 실행은 worker=1·queue=1·OpenCV 스레드=1이며 기동·저장을 포함한 배치입니다. CPU 모델은 기록되지 않았습니다. **Ubuntu 서버의 성능 기준이나 p95 보장값으로 사용할 수 없습니다.**

프로세스 Working Set·Private Bytes·누적 CPU를 100ms 간격으로 관측했습니다. 아래 메모리는 JVM·native·라이브러리를 포함한 프로세스 전체이며 요청 한 건의 추가 메모리가 아닙니다. 샘플 사이의 순간 최대값은 놓쳤을 수 있습니다.

| 단일 사진 | ALL | PRODUCTION |
|---|---:|---:|
| 배치 내부 시간 | 9.48초 | 9.03초 |
| JVM 기동~종료 | 10.54초 | 10.11초 |
| 누적 CPU 시간 | 11.59 CPU초 | 11.05 CPU초 |
| 최대 관측 Working Set | 285.5MiB | 260.6MiB |
| 최대 관측 Private Bytes | 516.6MiB | 509.6MiB |
| PNG+보고서 크기 | 약 21.6MiB | 약 9.12MiB |

### 반복·병렬 실행

같은 사진을 `PerformanceProbe`로 PRODUCTION 모드에서 처리했습니다. probe는 PNG를 메모리에서 생성하지만 파일 저장·HTTP·ZIP은 포함하지 않습니다. 매번 결과를 소비하고 전체 결과를 누적하지 않았으며 명시적 System.gc()도 호출하지 않았습니다.

| 조건 | 총 경과 시간 | 평균 처리량 환산 | 최대 Working Set | 최대 Private Bytes |
|---|---:|---:|---:|---:|
| worker 1, 순차 12장 | 103.27초 | 약 8.61초/장 | 347.2MiB | 502.9MiB |
| worker 2, 두 장씩 3회 | 47.12초 | 약 7.85초/장 | 462.0MiB | 650.3MiB |

두 worker 실행의 누적 CPU는 91.94 CPU초, 첫 두 장 동시 실행 round는 17.63초였습니다. 평균 처리량 환산은 개별 요청 지연 시간이 아닙니다. 이 PC에서는 worker를 두 배로 늘려도 처리량이 두 배가 되지 않았고 메모리는 더 사용했습니다.

순차 반복의 초·중·후반 Private Bytes 최대값은 502.8/502.4/502.9MiB로 유사했지만 Working Set은 증가했습니다. **12회·약 103초의 관측으로 장시간 누수 부재를 증명할 수 없습니다.** JVM GC·페이지 상주·native allocator의 영향도 포함합니다.

### Ubuntu에서 확인할 항목

Green House의 실제 업로드·저장 경로에서 같은 입력 세트로 worker 1과 2를 비교합니다. 이미지 크기·maxDimension·출력 모드·JDK/OpenCV·CPU/RAM·컨테이너 제한을 함께 기록합니다. 대표 양식의 처리 결과를 확인하면서 요청 지연 p50/p95, 처리량, 프로세스 RSS 또는 컨테이너 메모리, CPU, 거절 수와 장시간 반복 추이를 측정합니다. queue만 늘려 동시 처리량을 높이려 하지 않습니다.

코어·호스트 회귀 검증은 Green House backend에서 실행합니다.

```bash
./gradlew :slip-image-core:test check bootJar --no-daemon
```

기존 배치 측정을 원본 저장소에서 다시 실행하려면 별도로 준비한 사진 폴더를 사용합니다. 아래 시간은 파일 저장과 JVM 기동을 포함하며 코어 probe 수치와 직접 비교하지 않습니다.

```bash
bash mvnw -pl slip-image-demo -am package -DskipTests
/usr/bin/time -v java -Xmx1200m \
  -jar slip-image-demo/target/slip-image-processor-1.0.0.jar \
  --batch /path/to/photos /path/to/results \
  --max-dimension=2200 --workers=1 --queue-capacity=1 \
  --opencv-threads=1 --output-mode=PRODUCTION
```

Green House로 이식한 뒤에는 이 문서도 `docs/image-processing/PROCESSING.md` 등에 함께 보관합니다. 기존 Windows 수치는 기준 기록으로 남기고 Ubuntu 결과를 환경·입력·측정 방법과 함께 추가합니다.
